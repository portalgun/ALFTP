#+TITLE: alftp Code Audit
#+DATE: 2026-08-05

Audit of the =alftp= script (single-file bash tool wrapping lftp) covering
correctness bugs, unimplemented/half-implemented features, security concerns,
portability, and suggested improvements. Line numbers refer to the current
working-tree version of =alftp=.

* Critical / Confirmed Bugs
  Nothing open.

* Missing / Incomplete Features
  These are flags or config keys that are parsed and stored but never acted
  on — several are self-documented as such in the TODO block at the top of
  the file (alftp:23-26, 27-41), but it's worth cataloguing exactly what's
  dangling since the help text and =alftp.conf.template= advertise them as
  real, working options:

  - *~-rm~ (rm_remote)* — variable set (alftp:330) but unused; nothing in
    ~DLDR~/~DLFL~/~DOWNLD~ issues a remote delete beyond removing the
    completion symlink, so "remove files from remote location once download
    is complete" doesn't happen.
  - *~-r~ (no_append) and the "record" feature* — ~alftp.conf.template~
    documents a ~record~ option ("list of everything that has been
    successfully downloaded"), and ~-r~ is supposed to suppress appending to
    it, but no code anywhere reads ~$record~ or appends to any such file.
    Both the base feature and its suppression flag are entirely absent.
  - *~chkrmd~ / ~chkrmf~* (alftp:558-568) — defined, never called from
    anywhere. Likely meant to clean up stale local directories/files (maybe
    tied to the missing "old session" handling) but currently dead code.

* Security Concerns
  Nothing open.

* Correctness / Robustness Issues (non-critical)
   - *Done*: ~config_template~ holds a real, commented default config;
     ~mkdir -p "$(dirname "$config")"~ runs first and aborts with a clear error if
     it fails; the file is written with ~printf '%s'~. Verified end to end against
     a throwaway ~$HOME~.

** Dead/unused variables from the locking design that never landed
   :PROPERTIES:
   :LOCATION: alftp:375-376
   :END:
   ~ON=0~ and ~prevsession=0~ were set in ~WELCOME~ and never read again.
   They have since been dropped along with the rest of the ~WELCOME~ rewrite,
   but the feature they were scaffolding is still missing (see "Session
   locking" above), so this stays open until locking is implemented or the
   help text stops promising it.

* Portability

  - README explicitly states "Currently incompatible with mac" — likely
    causes include: GNU-specific ~sed -i 's/.../.../ ' file~ (no space before
    file arg needed for GNU, but BSD ~sed -i~ requires an explicit (even
    empty) extension argument — see alftp:413) and GNU ~find -regex~
    (alftp:580, uses POSIX awk-style regex which BSD find doesn't support the
    same way). The hardcoded ~/home/$USER~ path is fixed (see Completed).
    Worth either documenting the remaining incompatibilities or gating the
    relevant commands behind an OS check.

* Suggested Improvements / Possible New Features

  - *Finish or remove the half-built features*: for each of ~-n~, ~-o~,
    ~-fs~, ~-rm~, ~-r~/record, ~autoUncompress~, ~errors~, ~verify~ — either
    implement the documented behavior or remove the flag/config key and its
    mention in the help text and ~alftp.conf.template~ so the documented
    surface area matches what actually works.

* Completed
  Items resolved on 2026-08-23. Line numbers in the ~:LOCATION:~ drawers refer
  to the pre-fix version of =alftp=.

** DONE SSH key configuration (~keyfile~) never reaches lftp
   :PROPERTIES:
   :LOCATION: alftp:368-370
   :END:
   The ~set sftp:connect-program "ssh -a -x -i $keyfile"~ in ~ARGSC~ was a bash
   builtin reassigning the script's own positional parameters, not an lftp
   directive, so key-based SFTP auth silently did nothing.
   - *Done*: ~set_opts~ emits it as an lftp directive (quoted with
     ~lftp_quote~) when ~$keyfile~ is set, and the bogus ~set~ is gone. A real
     ~alftp.src.conf~ spells the key ~keyFile=~, so ~resolve_keyfile~ (called
     from ~WELCOME~) accepts either spelling and both are initialised in
     DEFAULTS. Covered by a bats test on ~set_opts~ for both spellings.

** DONE Session locking was promised but never implemented
   :PROPERTIES:
   :LOCATION: alftp:55-56, 375-376
   :END:
   The help text promised "Lock the current session" and ~COMPLETE~ removed
   ~/tmp/alftp.lock~, but nothing ever created or checked it, so two concurrent
   runs would clobber each other's list files.
   - *Done*: ~WELCOME~ takes the lock (~take_lock~), writing its pid with a
     ~noclobber~ redirect so the create is atomic. A lock whose pid is still
     alive refuses the run by name ("another run (pid N) is in progress"); one
     whose pid is gone is reported as stale and taken over. ~release_lock~ (only
     for a lock this process took) runs from ~COMPLETE~ *before* its ~exitflag~
     early return, so ~-jl~ gives it back too, and from the signal handler. The
     path is the new ~lockfile~ config key, default ~/tmp/alftp.lock~ -- the
     tests set it elsewhere so they cannot disturb a real run. The in-session
     helper (~ALFTP_EMIT_DL~) deliberately does not take it: its parent holds
     it. Covered by unit tests (live pid, stale pid, release) and an end-to-end
     test against the fake server.

** DONE ~-n~ (new_only) and ~-o~ (old_only) did nothing; ~-c~/~--continue~ replaces them
   :PROPERTIES:
   :LOCATION: alftp:310, 405
   :END:
   ~new_only~ was set and never read; ~old_only~ only skipped the whole
   download block, so neither flag did what the help text described.
   - *Done*: both flags and both globals are gone, and ~-c~/~--continue~ takes
     their place: ~CONTINUE_LIST~ (from ~EDIT_LIST~, right after ~FORMAT_LIST~)
     merges the marks in ~$oldfile~ -- the copy of the previous session's list
     that ~CREATE_LIST~/~SINGLE_SESSION~ take before the fresh listing
     overwrites it -- into this run's listing, so an entry marked last time
     comes up marked (~+~ or ~-~) if it is still on the server, and it says how
     many marks it carried over. ~$oldfile~ moved to ~WELCOME~ so the in-session
     helper, which never runs the session functions, agrees on it.
     ~marked_entries~ is the shared "what does this list file say" reader;
     ~tui_apply_marks~ puts the marks back into the picker's tree (~tui_load~
     strips markers on purpose), and the editor path leaves ~+~/~-~ lines
     uncommented under ~-c~. ~-ns~ still works -- it only ever needed
     ~suspend_old~ -- and ~COMPLETE~ now checks the old file exists before
     restoring it.

** DONE ~-fs~ (print_fs / filesize) was dead; ~-ls~ replaces it
   :PROPERTIES:
   :LOCATION: alftp:320, 30-38
   :END:
   ~print_fs~ was set and never read; the intended size arithmetic never got
   past the TODO block.
   - *Done*: ~-fs~ and ~print_fs~ are gone. ~-ls~ runs everything up to and
     including the picker, then prints each marked entry's name, size and date
     (~LIST_MARKED~, straight out of the columnar list file) and stops without
     transferring. In the single-session path the helper writes an empty emit
     file so the session has nothing to source, and the parent prints the list
     instead of running ~TYPE~/~POST_PROCESS~. Covered by a unit test and an
     end-to-end test that checks nothing was transferred or unlinked.

** DONE ~record~ / ~errors~ / ~verify~ config keys, and structured logging
   :PROPERTIES:
   :LOCATION: alftp.conf.template
   :END:
   All three were documented in ~alftp.conf.template~ and referenced nowhere in
   the script.
   - *Done*: ~POST_PROCESS~ now logs one tab-separated
     ~time<TAB>profile<TAB>entry<TAB>status~ line per entry -- greppable, and
     ~cut~-able by column. Entries that arrived go to ~$record~ (unless ~-r~ /
     ~no_append~), entries that did not go to ~$errors~, and ~checksum=True~
     writes what it verified to ~$verify~. All three default to
     ~$HOME/.cache/alftp/alftp.{record,errors,verify}~, alongside the existing
     ~listfile~/~logfile~ defaults, and their directories are created in
     ~WELCOME~. Whether an entry arrived is decided locally, by looking for it
     under ~$local_dl_dir~: lftp's own output goes to the terminal (and shares
     it with the picker in the single-session path), so there is no success line
     to read back. ~--dry-run~ and ~-cl~ skip the stage entirely, since neither
     downloaded anything. The profile name is kept in a new ~profile~ global,
     set in ~ARGSB~, so a line says which profile it came from.

** DONE ~autoUncompress~ was documented but inverted and unread
   :PROPERTIES:
   :LOCATION: alftp:430
   :END:
   The unrar path ran unconditionally unless ~-nu~ was passed, and
   ~$autoUncompress~ was never read.
   - *Done*: ~autoUncompress~ defaults to ~False~ and is what decides:
     ~UNRAR_FUN~ runs only when it is true (compared case-insensitively, like
     ~data~), and ~-nu~ still forces it off for a run where the config asked for
     it. Covered by a bats test with ~UNRAR_FUN~ stubbed, in all three
     combinations.

** DONE Checksum verification
   :PROPERTIES:
   :LOCATION: alftp:39 (TODO block)
   :END:
   Listed in the TODO block, never implemented, and tied to the unused
   ~verify~ config key.
   - *Done*: new ~checksum~ config key, default ~False~. When it is true,
     ~verify_entry~ writes a line per downloaded entry to ~$verify~ holding the
     size in bytes and, for a single file, its sha256 -- so what is on disk can
     be checked later against what was fetched.
     Two things it deliberately does *not* do, both found by trying them: it
     does not compare against the size in the listing, because the completed
     directory is full of symlinks and a server that reports the size of the
     link rather than of the file behind it (which is exactly what the file://
     test server does) makes every entry look wrong; and it does not use lftp's
     ~xfer:verify~, because its ~verify-file~ helper needs perl modules that are
     frequently missing (~String::CRC32~ here), and when it fails it fails the
     transfer -- which also swallows the ~&& rm -f~ that drops the symlink of a
     completed entry.

** DONE GPG-encrypted config
   :PROPERTIES:
   :LOCATION: alftp:53
   :END:
   The help text promised "Read config file and gpg file variables" and no gpg
   invocation existed anywhere in the script.
   - *Done*: new ~gpg_file~ config key naming a gpg-encrypted file of settings
     (typically one ~password=~ line). ~eval_gpg_config~ runs between the two
     config passes and the argument passes -- so either config file can name it
     and a CLI flag still wins -- decrypts with ~gpg --batch --quiet --decrypt~
     and ~eval~s the plaintext the way the rest of the config is eval'd, then
     drops it from the variable it came in. A missing file, a missing gpg or a
     failed decrypt each abort with a message naming the file rather than
     falling back to whatever credentials were lying around. Covered by bats
     tests with ~gpg~ stubbed (success and failure) and a missing file.

** DONE Password exposure and no non-plaintext credential path
   :PROPERTIES:
   :LOCATION: alftp.conf.template, alftp:511
   :END:
   The password no longer reaches ~ps~ (that part was already fixed), but the
   config file still had to hold it in plaintext.
   - *Done*: there are now three ways not to store it: ~keyfile~ (see above),
     ~gpg_file~ (see above), and prompting. ~prompt_password~ (in ~WELCOME~)
     asks with ~read -s~ when there is a username, no password and no keyfile --
     but only when stdin is a terminal, so a cron run keeps the current
     behaviour of an empty password rather than hanging. A password typed at the
     prompt reaches the in-session helper through ~ALFTP_PASSWORD~ on the ~!env~
     line (~child_env~), since the helper re-derives everything else from config
     plus argv and would otherwise have no credentials for the listing logins
     ~tab~ does; a child's environment is readable only by its owner, and the
     generated script already holds the same secret.

** DONE ~eval~ over untrusted-ish input
   :PROPERTIES:
   :LOCATION: alftp:169-197
   :END:
   ~eval_local_config~/~eval_remote_config~ ~eval~ chunks of ~alftp.src.conf~,
   which is inherent to the "profiles are bash snippets" design but worth
   saying out loud.
   - *Done*: no code change, as the audit suggested -- a callout instead, in
     both ~README.md~ (a block quote right where the file's bash-ness is first

** DONE ~chmod -R 777~ on downloaded directories
   :PROPERTIES:
   :LOCATION: alftp:433
   :END:
   Post-processing made everything downloaded world-writable.
   - *Done*: replaced by ~apply_perms~ and five config keys: ~chmod~
     (~True~/~False~, default ~False~) decides whether permissions are touched
     at all, ~perms_dirs~ (default ~744~) and ~perms_files~ (default ~644~) say
     what to; ~chown~ (default ~False~) and ~owner~ do the same for ownership.
     The default is therefore to change nothing at all -- content keeps the
     permissions and owner it arrived with. Covered by a unit test (nothing
     changes unless asked) and an end-to-end test.

** DONE Regex-injection via hostname / default_server
   - *Done*: verified -- ~ere_escape~ escapes ERE metacharacters for both the
     hostname and ~default_server~ before they are spliced into the ~awk~
     patterns, and the bats test that distinguishes ~example.com~ from
     ~exampleXcom~ in the fixture passes. Nothing further to do; this is the
     same fix already recorded under "Unescaped values embedded into awk regex".

** DONE No traps set despite ~COMPLETE~ clearing them
   :PROPERTIES:
   :LOCATION: alftp:548
   :END:
   ~COMPLETE~ cleared traps the script never installed, so a Ctrl-C mid-run
   left its temp files and (once locking existed) its lock behind.
   - *Done*: ~install_traps~ (from ~WELCOME~) installs INT/TERM/HUP handlers
     that release the lock, remove the temp files the run created, and re-raise
     the signal after clearing the trap, so the caller sees an interrupted
     process rather than exit 0. To make "the temp files the run created"
     knowable, every ~mktemp~ now goes through ~new_tmp~, which records the name
     in ~$tmpfiles~ (it returns the name in ~$tmpfile_new~ rather than on
     stdout, because a ~$(...)~ would put the array append in a subshell);
     ~ALFTP_DEBUG~ still keeps them. ~COMPLETE~ clears the same three signals it
     now installs. The picker's own INT handling is unaffected: ~tui_open~ saves
     and ~tui_close~ restores whatever traps were in place. Covered by two bats
     tests that send the running shell INT and TERM and check the lock and the
     temp file are gone and the exit status is 130/143.

** DONE No strict-mode / typo protection
   - *Done*: audited, and the answer is that ~pipefail~ stays off, deliberately.
     ~set -u~ is on and every optional flag and config key is initialised in the
     DEFAULTS block. ~-e~ stays off for the reason already recorded: too much of
     the control flow uses a command "failing" as a normal outcome. For
     ~pipefail~, the pipelines in this script fall into two groups, and neither
     wants it: the config and list transforms
     (~eval_local_config~/~eval_remote_config~/~TYPE~/~marked_entries~) end in
     ~grep~/~sed~ whose "failure" is simply "nothing matched", which is a normal
     result here; and no pipeline in the script has its exit status consumed --
     the places that do check a status (~run_lftp_script~, ~FORMAT_LIST~'s
     ~... > tmp && mv~, ~tui_fetch~) run a single command, so they already
     report the failure that matters. Turning ~pipefail~ on globally would
     therefore change nothing except to make the deliberate empty-grep cases
     look like errors. Worth revisiting if a pipeline whose status is checked
     ever appears.

** DONE ~-ld~/~-rd~ set the wrong flags, breaking non-profile CLI usage
   :PROPERTIES:
   :LOCATION: alftp:295-304, alftp:349-356
   :END:
   In ~ARGSC~:
   #+begin_src bash
   -ld)
       lastParam="$i"
       nextParam="ld"
       sourcelfag=1        # typo: "sourcelfag", not "sourceflag" — and wrong flag anyway
       ;;
   -rd)
       lastParam="$i"
       nextParam="rd"
       destflag=1          # should be sourceflag=1
       ;;
   #+end_src
   ~-ld~ (local/destination dir) sets a misspelled, otherwise-unused variable
   ~sourcelfag~ instead of ~destflag~; ~-rd~ (remote/source dir) sets ~destflag~
   instead of ~sourceflag~. The end-of-function check requires both
   ~destflag~ and ~sourceflag~ to be non-empty:
   #+begin_src bash
   if [[ -z $destflag ]]; then echo "Please specify desitnation."; exit 0; fi
   if [[ -z $sourceflag ]]; then echo "Please specify source."; exit 0; fi
   #+end_src
   Result: running alftp the way the README/help text documents —
   ~alftp -s server -u user -p pass -P port -ld /local -rd /remote~ (i.e.
   without ~-i~/~-a~) — *always* exits with "Please specify source.", even
   though ~-rd~ was given. This appears to make the entire non-profile /
   direct-flag invocation mode of the script non-functional.
   - *Fix*: rename ~sourcelfag~ → ~destflag~ under ~-ld~, and change ~-rd~ to
     set ~sourceflag=1~.
   - *Done*: ~-ld~ now sets ~destflag=1~ and ~-rd~ sets ~sourceflag=1~; the misspelled
     ~sourcelfag~ is gone. ~ARGSB~ also had to be fixed: selecting a profile that
     already defines ~remote_dl_dir~ set ~destflag~ but never ~sourceflag~, so
     ~-i~/~-a~ hit the same "Please specify source." dead end. It now sets
     ~sourceflag=1~ whenever a profile is selected.

** DONE Post-download processing loop iterates over files instead of directories
   :PROPERTIES:
   :LOCATION: alftp:426-435
   :END:
   #+begin_src bash
   while read -r line; do
       if [[ -z $line ]]; then continue; fi
       if [[ -z $nounrar ]]; then
           UNRAR_FUN "$line"
       fi
       find -path "$line" -type d -exec chmod -R 777 {} \;
       find -path "$line" -type f -exec chmod 644  {} \;
   done <<< "$LINESF"
   #+end_src
   This loop — which unrars archives and fixes permissions recursively — reads
   from ~$LINESF~ (the *files* list) instead of ~$LINESD~ (the *directories*
   list). Since ~UNRAR_FUN~ does a recursive ~find~ for ~*.rar~ inside its
   argument and the ~chmod -R 777~ only matches ~-type d~, this logic is
   meaningless applied to individual downloaded files, and mirrored
   directories (the typical case for release-style downloads with rar sets)
   never get unrared or permission-fixed at all. Combined with the preceding
   loop (also over ~$LINESF~, doing a plain ~chmod 644~), files get touched
   twice and directories never get touched.
   - *Fix*: change the second loop to ~done <<< "$LINESD"~.
   - *Done*: the unrar/permission loop now reads from ~$LINESD~.

** DONE ~find -path "$line"~ doesn't target the actual download location
   :PROPERTIES:
   :LOCATION: alftp:433-434 (and the UNRAR_FUN call above it)
   :END:
   Downloaded content lands in ~"$local_dl_dir"/"$line"~ (see ~DLDR~/~DLFL~),
   but the post-processing calls ~find -path "$line" ...~ with no starting
   directory, which defaults to searching from the script's current working
   directory and matches ~-path~ against relative paths from there. Unless
   the script happens to be invoked with ~cwd == $local_dl_dir~, this ~find~
   will not match the just-downloaded files/dirs at all.
   - *Fix*: search under ~"$local_dl_dir/$line"~ explicitly, or ~cd
     "$local_dl_dir"~ first.
   - *Done*: post-processing now operates on ~"$local_dl_dir/$line"~ (and skips entries
     that do not exist), for the ~chmod 644~ file loop as well. The ~SsS~
     trailing-whitespace sentinel is translated back to a space first, the same
     way ~DLDR~/~DLFL~ do it.

** DONE ~data=true~ vs ~data=True~ case mismatch defeats the complete/data-dir fallback
   :PROPERTIES:
   :LOCATION: alftp:339, alftp:359-366
   :END:
   ~-d~ sets ~data=True~ (capital T), and the effective remote directory is
   chosen with ~[[ $data == True ]]~ (case-sensitive comparison):
   #+begin_src bash
   if [[ -z $complete_dir ]] && [[ ! -z $data_dir ]]; then
       data=true              # lowercase — will never match "True" below
   fi
   if [[ $data == True ]]; then
       remote_dl_dir="$data_dir""$remote_dl_dir"
   else
       remote_dl_dir="$complete_dir""$remote_dl_dir"

   The fallback branch (used when only ~data_dir~ is configured and
   ~complete_dir~ is not) sets ~data=true~, but the check two lines later
   requires ~True~. So when a profile only defines ~data_dir~ (a
   documented, valid configuration per ~alftp.conf.template~), ~remote_dl_dir~
   is built with the empty ~$complete_dir~ instead of ~$data_dir~, producing a
   wrong/incomplete remote path.
   - *Fix*: use ~data=True~ for consistency (or switch both checks to a
     case-insensitive / boolean-ish test).
DO BOTH
   - *Done*: the fallback sets ~data=True~ *and* the test is now case-insensitive
     (~${data,,} == true~), as requested.

** DONE Config bootstrap writes the literal string "config_template", not its contents
   :PROPERTIES:
   :LOCATION: alftp:98-100, alftp:133
   :END:
   #+begin_src bash
   config_template="

   "
   ...
   echo config_template > $config
   #+end_src
   ~config_template~ is (a) unquoted so the literal word ~config_template~ is
   written to the file instead of the variable's contents, and (b) itself
   empty, so there's nothing useful to write even if quoted correctly. On top
   of that, ~$config~'s parent directory (~~/.config/alftp/~) is never
   created, so first-run bootstrap will fail with "No such file or directory"
   on a fresh machine (the very case this code path exists for) rather than
   creating anything.
   - *Fix*: populate ~config_template~ with real default content (or ship
     ~alftp.conf.template~ alongside the script and copy it), ~mkdir -p
     "$(dirname "$config")"~ before writing, and use ~echo "$config_template"
     > "$config"~ / better, ~printf '%s\n' "$config_template" > "$config"~.

** DONE Unescaped values embedded into awk regex
   :PROPERTIES:
   :LOCATION: alftp:170, alftp:186
   :END:
   #+begin_src bash
   I=$(hostname)'\\|*[A-Za-z0-9._]*\\]'
   ...
   I='\\|'"$default_server"'\\]'
   #+end_src
   Both the local hostname and the configured ~default_server~ are spliced
   directly into an ~awk~ extended regex with no escaping. Any regex
   metacharacter in the hostname or server name (a literal ~.~ is the common
   case — hostnames routinely contain dots) changes what the pattern matches
   rather than raising an error, so profile selection can silently pick the
   wrong block or none at all.
   - *Done*: new ~ere_escape~ helper escapes ERE metacharacters (doubling the
     backslashes, since ~awk -v~ processes escapes itself) for both the hostname
     and ~default_server~. Covered by a bats test using a fixture with both
     ~example.com~ and ~exampleXcom~ profiles.

** DONE Non-anchored ~grep -v~ filter can drop unrelated config lines
   :PROPERTIES:
   :LOCATION: alftp:172
   :END:
   #+begin_src bash
   grep -vE "(port|user|dataDir|watchDir|completeDir|pass|srcs)"
   #+end_src
   This is meant to strip remote-only keys (~port~, ~username~, ~password~,
   …) out of the local config chunk, but the pattern isn't anchored to the
   start of the line or to ~key=~, so it matches the substring anywhere,
   including inside *values*. A profile line like
   ~local_dl_dir='~/Downloads/important'~ contains the substring ~port~ (from
   "important") and would be silently dropped from the local config. Anchor
   the pattern, e.g. ~grep -vE "^(port|user...)="~.
   - *Done*: the pattern is anchored to the start of the line
     (~^(port|user|dataDir|watchDir|completeDir|pass|srcs)~). It is anchored
     without requiring a trailing ~=~ so the ~user~/~pass~ prefixes keep matching
     ~username=~/~password=~. Covered by a bats test on a profile whose
     ~dl_dir~ value contains "important".

** DONE Help/copyright/warranty text is fed through ~printf~ as a format string
   :PROPERTIES:
   :LOCATION: alftp:154, 158, 162
   :END:
   #+begin_src bash
   printf "$help"
   #+end_src
   Passing a variable as printf's *format* argument means any ~%~ or
   backslash escape sequence embedded in the text is interpreted rather than
   printed literally. Currently the text is escape-sequence-free, so it
   happens to work, but it's a latent footgun the moment someone edits
   ~$help~ to include a literal ~%~ (e.g. documenting a percentage option).
   Use ~printf '%s\n' "$help"~ instead.
   - *Done*: all three now use ~printf '%s\\n'~.

** DONE Useless use of ~cat~ / unanchored grep for ~default_server~
   :PROPERTIES:
   :LOCATION: alftp:181
   :END:
   #+begin_src bash
   def=$(cat "$configsrc" | grep "default_server")
   #+end_src
   No anchor and no comment-exclusion, so a commented-out
   ~#default_server=...~ line, or any line merely mentioning the phrase, would
   also match and get ~eval~'d.
   - *Done*: ~grep -E '^[[:space:]]*default_server=' "$configsrc" | tail -n 1~.

** DONE ~listfile~ has no default and no validation
   :PROPERTIES:
   :LOCATION: alftp:377
